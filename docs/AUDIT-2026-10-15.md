# VELO engineering audit — 15 October 2026

## Decision

Keep VELO an explicitly restricted, testnet-only prototype. Do not market this release as audited, mainnet-ready, fully noncustodial infrastructure without operational trust, or a verified-performance network. The hosting migration works within the inspected evidence. Core accounting and legacy authorization still need remediation.

This is a source/infrastructure engineering review, not a licensed financial opinion, independent penetration test, formal verification or third-party contract audit. A source finding is distinct from a reproduced bug; a unit test is distinct from an end-to-end browser test.

## Trading/risk gaps

- `originalNotional` is not consistently conserved through partial close and collateral changes. Size must be an independent quantity; adding margin must not create historical PnL.
- Cross margin is not a complete portfolio-wide risk model. UI buying power, account equity, reserved collateral and liquidation logic require one consistent definition.
- Conditional execution needs a fresh tradability check. Reduce-only targeting must be explicit and unable to increase/reverse a position; its trigger semantics must match an exit. It is blocked in the UI pending redesign.
- TP/SL registration is separate from opening the trade. Failed protection setup must be visible and recoverable; no atomic-protection claim is justified.
- One-minute scans, bounded batches, RPC outages and price gaps can delay execution. Trigger levels are not fill guarantees. Test both sides of limit/stop and TP/SL, partial fills/closure, cancellation races, insufficient gas and restart recovery.
- Current stop rules relative to entry restrict profit-locking stops. Standard trailing/advanced orders are not implemented.
- There is no production-ready funding-rate, open-interest/skew, insurance, loss-allocation or liquidation/maintenance-margin design. These cannot be inferred from common Solidity libraries.
- Deposits/payouts and mock liquidity are testnet mechanisms; faucet/owner minting is not real stablecoin backing. Do not infer solvent real-money operations from token balances on testnet.

## Social, dashboard and interface review

The app implements posts, replies, likes, reposts, follows, profile/wall views, mentions, sharing and notifications. This is not yet an industry-grade social network: moderation/report/block tools, anti-spam quotas, abuse handling, trusted performance indexing, authorization tests and operational processes remain gaps.

The old copy action merely mirrored database positions and adjusted client balances. It is now disabled with an explicit planned-feature message. No new simulated copy positions are created by that action. Historical simulated data was not deleted or declared on-chain.

Chart controls that referenced an undefined setter were corrected. Username onboarding now matches the registry's 3–16 lowercase rules and letter-first constraint. Settings reads/writes the private contact API and no longer claims email alert delivery. The market volume panel is labelled as reported activity; conditional orders are not an executable matching book.

Dashboard PnL, activity, profiles and leaderboards need a canonical chain indexer with event identities, confirmation/reorg handling and deduplication. Client-authored metrics cannot be used for financial authorization or claims of tamper-proof performance. Optimistic UI must reconcile failed transactions and display loading/empty/error states distinctly.

Browser acceptance still required: fresh/returning login; rejected signature; wrong chain; wallet change/disconnect; expired session; funding/faucet/withdraw/send; trade confirmation/revert; TP/SL edits; profile/username/avatar edits; follow/unfollow; nested replies; like/repost/mentions; notification ownership/read state; dashboard filters; deep links/back; mobile menus and keyboard focus; chart interaction; logout/recovery. Browser verification was blocked in this environment, so these are not reported as passed.

## Reported UX failures and repairs

On 15 October the owner reported unreliable wallet reconnect, hanging fills, false empty public feeds, stale data, missing inactivity logout and disappearing private-key controls/tooltips. Review found concrete frontend causes:

- An asynchronous `onAuthStateChange` callback awaited further calls on the same Supabase client, risking the documented auth-lock deadlock. It now defers hydration outside the callback. A regression test uses the real Supabase client to verify subsequent session reads finish.
- Public profiles/posts/fills depended on token refresh. They now use a separate anonymous read client, retaining existing RLS. Direct anonymous checks returned 32 profiles, seven posts, two follows and at least 100 trade-history rows. These are database records, not verified active users or genuine volume.
- Fills converted a watchdog timeout into an empty state. Requests now have a timeout, explicit error/Retry, reconnect/focus/poll refresh and a separate successful-empty state. Public caches expire after five minutes; successful empty reads clear deleted results.
- Settings depended on a fresh profile object every render, resetting private-key confirmation/reveal. It now depends on stable identity fields. Trade-detail row components are stable across price changes; focus/hover tooltip handling is improved.
- Explicit logout no longer wipes all browser/connector storage or requires a hard refresh. A 30-minute inactivity timer warns for 60 seconds, and an eight-hour app-session limit requires re-login. Public browsing remains available. This is a client session policy, not encrypted-key storage or immediate on-chain permission revocation; keepers continue and open trades remain open.
- Explicit sign-in requires a fresh signature, deduplicates concurrent requests and rejects late signatures after cancellation. Recovery retains the old key on cancellation or a derived-address mismatch.
- Profile saves report persistence failures instead of unconditional success. Profiles show their author's posts; composing on another person's wall is disabled in the UI. Existing wall records are retained, and the database authorization cutover remains pending.

Four component-level DOM tests cover key reveal across rerenders, tooltip stability, fills error/retry and true empty fills. Additional tests cover auth locking, cancellation/concurrency, inactivity/absolute expiry and wallet recovery. These use synthetic fixtures, not a complete real-browser wallet journey. The available browser binary download failed; no claim of authenticated browser/mobile verification is made.

Posts/comments already have database IDs and nested post/comment routes. Repost-specific pages, richer profile editing, moderation/blocking and a full account/notification interaction matrix still need work. None of these interface fixes resolves the pending database authorization or contract defects.

## 16 October addendum: false liquidation and delayed data

The owner's SOL long (trade 108) was manually closed, but the browser inferred liquidation from its disappearance from the open-position list. It recorded the entire collateral as lost. A failed position RPC could also produce an empty/partial snapshot and trigger this incorrect inference.

The successful Base Sepolia [closing receipt](https://sepolia.basescan.org/tx/0xccd976d0fbd3905b395482d67e546bb88f394b28a4a2c2f882991a3e7a78bb99), block 48160131, contains `PositionClosed`: exit price 105.14079832, realized PnL −63.745528 mUSDC, closing fee 0.998875 and payout 997.876912. It does not contain a liquidation event. The one identified history row and its liquidation notification were backed up and corrected with guarded updates. No funds were moved and no other history rows were rewritten.

The frontend now classifies closures from matching contract/trader/trade receipt events. Full closes through the partial-close modal use the full-close event; trigger reasons come from `TriggerFired`. Deterministic event IDs deduplicate manual handlers and reconciliation. Cancelled conditional orders cannot be inferred as fills from an unrelated position in the same market. Failed RPC reads retain the last confirmed snapshot and display a retry message instead of inventing closed positions.

Transactions return after receipt confirmation without awaiting another full account refresh. Delayed confirmation retains the submitted hash, displays an explorer link and blocks repeat submissions until its status is resolved. This is a local guard, not a distributed transaction coordinator across browser tabs/devices. Browser price simulation no longer closes or liquidates on-chain positions; scheduled keepers remain responsible for those actions.

The newer native chart and share-card changes from commit `51016ca` are retained. Initial history now requests at most 300 source candles, with older history loaded when panning; concurrent requests share a short-lived cache. A slow authenticated Pyth page starts an explicitly labelled exchange fallback after two seconds, and first-page loading has an overall deadline. Signed-out charts do not wait for authentication. Exchange candles are not overwritten with Pyth ticks, and unavailable data is not replaced with invented prices. These changes reduce initial history requests; actual account-level Pyth usage savings have not been measured.

The merged suite passes 91 Node tests and TypeScript checking; the production build passes with large-bundle and vendor-chunk warnings. Five new history tests use mocked providers, and eleven receipt tests cover manual/partial/liquidated outcomes, rejected receipts, failed reads and cancelled/linked orders. They consume no live Pyth quota. Wallet/mobile acceptance remains separate.

Remaining limits: browser reconciliation searches only the most recent 10,000 blocks and is not a durable indexer. Historical/offline fills, multiple-client reconciliation, reorg handling and trusted server-owned performance still need a canonical event ledger. Liquidation events omit full realized PnL, so legacy collateral/cross-ledger limitations remain. A receipt-backed display fix does not correct the deployed contract's accounting defects.

## Contract replacement acceptance plan

1. Specify balance conservation for isolated and cross collateral, order escrow, realized PnL, fees, bounties and withdrawable reserves. Decide whether to implement a custom engine at all or integrate an established execution system after independent review.
2. Separate position size from margin. Define partial-close rounding, fees, pair disablement, reduce-only targeting and risk limits explicitly.
3. Create unit, fuzz and invariant tests: flat/positive/negative PnL, multiple users, adversarial ordering, long/short, liquidation, partial closes, margin changes, stale/future/confidence data, insufficient reserves and pause/restart. Conservation and solvency must hold under randomized sequences.
4. Obtain independent Solidity/risk review. A green internal suite alone is not a launch gate.
5. Deploy a new testnet contract and verify reproducible bytecode/configuration. The existing V3.1 is not treated as upgradeable.
6. Inventory open positions, pending orders, cross balances and token approvals. Preserve legacy close/cancel/withdraw access and keeper coverage while draining. Do not blindly replace the address and strand existing users.
7. Run isolated canary wallets and a supervised cohort; publish known limitations and incident contacts. Only then plan real-money legal, liquidity, security and operations work.

## Account/social cutover

Automatic approval review rejected the broad production SQL because it nulls public emails, deletes wallet passwords/sessions and changes policies/triggers across many tables, with lockout and social outage risk. **It was not executed.** The file is now `audit-plans/account-social-hardening.pending.sql`, outside the automatic migrations directory.

A smaller additive migration was applied: private contact storage/APIs and restrictive notification reads. It intentionally does not erase historical emails or retire all old credentials. See [the reviewable cutover plan](../audit-plans/README.md) for fixtures, backup, user impact and rollback requirements. Approval is still needed for the disruptive cutover after staged validation.
